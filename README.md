# Картинная галерея — ИДЗ 1, вариант 16

Нестеров Дан Александрович, БПИ253. C17, libc/POSIX, **один процесс и один поток**.
Вахтёр и посетители — самостоятельные сущности модели; параллельная деятельность
имитируется последовательной обработкой событий. Никаких pthread/fork/IPC в программе.

## Сборка и быстрый запуск

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
./build/gallery --config configs/demo.env --strategy cyclic --seed 7
./build/gallery --visitors 5 --capacity 2 --paintings 3 --delay-ms 50
./build/gallery --help
```

По умолчанию: 200 посетителей, 7 картин, 20 мест в галерее, 3 у картины,
прибытия через 1..5 мс, осмотр 10..30 мс, random, seed=42, без задержки вывода.
Для сборки нужны CMake ≥ 3.20 и C-компилятор. `build/compile_commands.json`
экспортируется автоматически для Ninja/Makefile-генераторов; его используют
clangd и target clang-tidy. База содержит семь команд обычной сборки, без
дублирования команд sanitizer. На macOS SDK явно указывается в этих командах.
Миллисекунды — время **модели**, не обещание длительности реального запуска.
`--delay-ms` задаёт реальную паузу после события, в том числе в quiet-режиме;
на моделируемые времена и результат она не влияет. Это не пустой цикл ожидания.

`gallery.jsonl` содержит подробный структурированный лог, `results.csv` —
добавляемую строку статистики. Лог перезаписывается при запуске; для хранения
нескольких дней выбирайте разные `--log`. `--log -` / `--journal -` отключают
соответствующий файл. Лог и журнал не могут ссылаться на один файл.

Обычный stdout — русские предметные события и итог. `--json` выводит JSONL,
`--quiet` — только итоговый JSON. Все файловые записи используют дескрипторы.
В JSONL ID посетителей и картин начинаются с 1; 0 означает отсутствие участника
или картины у служебного события. Номера seq включают конфигурацию, статистику и итог.
CSV защищён POSIX-блокировкой на время записи заголовка и строки, поэтому
независимые экземпляры могут добавлять результаты в один журнал на локальной ФС.
Занятый журнал ожидается ограниченно (до 1000 попыток с паузой 1 мс);
сигнал прерывает ожидание. Невозможность сохранить журнал считается I/O-ошибкой
с кодом 1, даже если остановка была вызвана сигналом.

## Ввод и конфигурация

```sh
./build/gallery --interactive
./build/gallery --config configs/demo.env --visitors 100 --strategy least-crowded
GALLERY_SEED=91 ./build/gallery --quiet --visitors 200
```

Приоритет: значения по умолчанию < файл < известные переменные среды < CLI.
Интерактивный режим явно запрашивает основные параметры и имеет последний приоритет:
вместимость, число картин, места у картины, посетители, min/max прибытия,
min/max осмотра, стратегия. EOF или некорректное значение завершает ввод с ошибкой.
Подсказки идут в stderr, поэтому stdout в quiet-режиме остаётся машинным JSON.

Файл — небольшая грамматика `KEY=VALUE`, пример в `configs/demo.env`. Поддержаны
пустые строки, отдельные комментарии `#`, пробелы вокруг ключа/значения. Ключи:

| Ключ | CLI |
|---|---|
| `GALLERY_CAPACITY` | `--capacity` |
| `GALLERY_PAINTINGS` | `--paintings` |
| `GALLERY_PAINTING_CAPACITY` | `--painting-capacity` |
| `GALLERY_VISITORS` | `--visitors` |
| `GALLERY_ARRIVAL_MIN`, `GALLERY_ARRIVAL_MAX` | `--arrival-min`, `--arrival-max` |
| `GALLERY_VIEW_MIN`, `GALLERY_VIEW_MAX` | `--view-min`, `--view-max` |
| `GALLERY_STRATEGY`, `GALLERY_SEED` | `--strategy`, `--seed` |
| `GALLERY_DELAY_MS`, `GALLERY_MAX_ACTIVE` | `--delay-ms`, `--max-active` |
| `GALLERY_LOG`, `GALLERY_JOURNAL` | `--log`, `--journal` |
| `GALLERY_UNLIMITED`, `GALLERY_QUIET`, `GALLERY_JSON` | соответствующие флаги |

Булевы значения в файле/среде — 0 или 1; `--finite` отменяет unlimited.
Не поддерживаются `export`, кавычки, подстановки `$VAR`, shell-команды и комментарии
в конце значения. Файл **не исполняется**; неизвестные и повторные ключи отклоняются.
Синтаксис не зависит от интерполяции `.env` в Docker Compose.

Границы: вместимости 1..10000, картин 1..256, посетителей 0..100000,
интервалы прибытия 0..1000000 мс, осмотра 1..1000000 мс, задержка 0..60000 мс,
активных записей 1..10000. Min не больше max. Число посетителей 0 — пустой день.

## Стратегии и завершение

- `ordered`: по возрастанию номера картины.
- `random`: равномерный выбор из ещё не осмотренных.
- `least-crowded`: минимальное число зрителей плюс ожидающих; при равенстве
  меньший номер. В последовательной модели снимок точный.
- `cyclic`: `(start + k * step) mod M`, где `gcd(step, M)=1`. Начало/шаг зависят
  от seed и ID посетителя; для одной картины шаг 0. Простота числа не обязательна.

Вход и каждая картина имеют FIFO. При заполненной выбранной картине посетитель
ждёт именно её, не перескакивает на другую. Все интервалы просмотров могут
пересекаться в логическом времени, хотя события обрабатывает один поток.

После последнего прибытия новых посетителей больше нет; вахтёр обслуживает
оставшуюся очередь. День заканчивается после выхода всех посетителей.

```sh
./build/gallery --unlimited --delay-ms 5
```

Ctrl+C / SIGTERM прекращает цикл, освобождает места и сохраняет частичный итог.
Начатый, но не завершённый осмотр не засчитывается. Ожидания ещё не допущенных
посетителей отдельно отражены как `pending_*_wait_ms`, а не примешаны к среднему.
В unlimited постоянно нулевой интервал прибытия запрещён: иначе время не продвигается.

Записи завершивших посетителей переиспользуются. Если очередь прибытий требует
больше `--max-active`, программа заканчивается с явной ошибкой и частичной
статистикой; посетители не отбрасываются молча. RAM ограничена, но лог unlimited
может расти: для долгих запусков выбирайте `--log -` или контролируйте размер файла.

Коды выхода: 0 — нормальный день; 1 — выполнение/I/O/лимит/инвариант;
2 — входные данные; 130 — SIGINT; 143 — SIGTERM. Начальные ошибки открытия файлов
не могут гарантировать запись итога в недоступный файл; диагностика идёт в stderr.

## Проверка и эксперименты

```sh
ctest --test-dir build --output-on-failure
cmake --build build --target sanitize
cmake --build build --target clang-tidy
python3 tests/run.py --binary build/gallery --jobs 8
cmake --build build --target experiments
```

Для статического анализа нужен `clang-tidy`; другой исполняемый файл можно выбрать
при конфигурации: `cmake -S . -B build -DCLANG_TIDY_EXECUTABLE=/path/to/clang-tidy`.
Target проверяет все C-файлы с флагами из `build/compile_commands.json`.
`cmake --build build --target check` собирает программу и запускает те же тесты;
перед отдельным `ctest` нужно собрать программу. Python, clang-tidy и Typst
находятся при конфигурации; соответствующие targets доступны при наличии tools.
Ошибки компилятора и анализатора приводят к неуспеху; эвристические рекомендации
`bugprone`, `performance`, `portability` выводятся как предупреждения.
`.clang-format` задаёт стиль LLVM, отступ 4 пробела и ширину 80 символов.
Явное форматирование: `clang-format -i src/*.c include/*.h include/internal/*.h`
(нужен `clang-format`).

Тестер — отдельный Python-процесс. Его ограниченный пул запускает независимые
процессы симуляции параллельно; каждому выделяется временный каталог. Только
тест одновременной записи намеренно использует общий CSV. Сам симулятор остаётся
однопоточным. Python нужен для тестов/анализа, но не для запуска C-программы.

`tests/validate.py` независимо восстанавливает посетителей, FIFO, занятые места,
время осмотра и интегралы загрузки из JSONL. Проверяются пять инвариантов,
воспроизводимость, сигналы, лимиты, config/env/CLI, ошибки записи и крайние случаи.
Структура 47 тестовых групп и назначение файлов описаны в [tests/README.md](tests/README.md).

Эксперименты: 4 стратегии × 24 seed × 2 нагрузки = 192 дня, по 200 посетителей.
Сравниваются одинаковые прибытия и длительности для пар посетитель/картина.
`output/experiments/summary.json` и `.csv` содержат агрегаты; `batch-*` — все строки
журнала, итоги и 8 подробных трасс для seed=0. Старые серии не удаляются.
Задержка в экспериментах равна нулю; каждая стратегия получает свои ID и RNG.

## Linux через Docker

```sh
docker compose run --build --rm gallery
docker compose run --build --rm gallery --visitors 100 --quiet --strategy ordered
docker compose --profile test run --build --rm tests
docker compose --profile experiments run --build --rm experiments
```

Dockerfile имеет отдельные targets `runtime`, `test`, `experiments`. Один контейнер
запускает один последовательный симулятор; target тестирования запускает несколько
независимых экземпляров. Результаты сохраняются в host `output/runs` / `output`.
Нужен работающий Docker daemon. Проверка YAML не является проверкой выполнения Linux.
На Linux/ARM64 проверены сборка всех трёх образов, 47 групп тестов (также с
ASan/UBSan), сохранение результатов и 192 запуска экспериментов.
Актуальное состояние проверки см. `docs/verification.md`.

## Отчёт и изучение

API-документация: установите Doxygen и повторите конфигурацию CMake, затем:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target docs
```

Откройте `build/docs/html/index.html`. Target `doxygen` — синоним `docs`.
Генерация HTML запускается явно и требует только Doxygen; Graphviz и LaTeX
не используются. Обычная сборка и запуск не зависят от генератора документации.
Конфигурация: `docs/Doxyfile.in`; обзор для разработчика: `docs/api.md`.
Комментарии в `include/` описывают структуры, контракты функций, владение ресурсами
и ошибки. Комментарии есть у каждой функции в `src/`, включая static-помощники;
они также включены в документацию. XML для проверки покрытия — `build/docs/xml`.
Ошибки документирования приводят к неуспеху target. Без установленного Doxygen
CMake продолжает работать и сообщает, что targets документации недоступны.
Для Doxygen 1.18.0 на macOS ARM64 target использует обход
[зарегистрированного падения парсера](https://github.com/doxygen/doxygen/issues/12326):
до трёх попыток только при SIGBUS/SIGSEGV или зависании (30 секунд на попытку).
Обычные ошибки документации завершают target сразу; исчерпание попыток тоже
считается ошибкой. Это обход неисправности внешнего инструмента, не исправление
его парсера.

```sh
cmake --build build --target report
```

Отчёт: `report/main.typ` → `output/pdf/report.pdf`. Для сборки нужны Typst и
данные `output/experiments/summary.json` (создаются target `experiments`). PDF содержит
условие, модель, запуск, проверки и сравнение стратегий, а также краткое
раскрытие использования ИИ и исправлений.
Рендер проверяется отдельно с Poppler. Typst использует project root через `--root .`.

Порядок изучения: `src/main.c` → `include/config.h` → `src/config.c` →
`include/internal/model.h` → `src/simulation.c`.
В simulation сначала прочитайте `push/pop`, затем `arrive/admit`,
`choose_or_leave/start_waiters`, `finish_view`, наконец `next_completion` и цикл
в `simulate`. `src/strategy.c` содержит RNG и выбор картины;
`src/invariants.c` — проверку состояния; `src/output.c` — открытие/закрытие лога,
синхронный вывод, CSV и статистику; `src/signals.c` — обработчики сигналов.
Каждому модулю соответствует `include/<module>.h`; объявленные там функции и
внешние переменные определяются в `src/<module>.c`. Приватный `model.h` содержит
только типы, без функций. Все модули вызываются одним потоком.
`docs/design.md` объясняет следующий шаг через маленький пример.
Результаты ревью и причины рефакторинга: `docs/code-review.md`.

Использование ИИ раскрыто в отчёте. Автоматические проверки и разбор
агентом не заменяют личную проверку студентом: перед сдачей нужно самостоятельно
прочитать код и уметь объяснить инварианты, завершение и результаты экспериментов.
